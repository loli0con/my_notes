# HTTP编码

## URL
URL（统一资源定位符）在RFC3986中规定，其路径和参数只能包含**非保留字符**:
* 字母：A-Za-z
* 数字：0-9
* 短横线：-
* 点：.
* 下划线：_
* 波浪号：~

任何除此之外的字符必须转换为**百分号编码**：
1. 先将字符转换为字节序列（现代标准强制要求使用UTF-8）
2. 将每个字节转换为%加上两位十六进制数

示例：中文字符（`你好`） -> UTF-8字节（`E4 BD A0 E5 A5 BD`） -> 添加百分号（`%E4%BD%A0%E5%A5%BD`）

## Header
HTTP协议最早设计时，其首部（包括请求行、状态行和**Header字段**）被严格定义为US-ASCII字符集。

由于ASCII仅支持7位字符，无法直接表示中文、日文等非拉丁字符。为了在Header（如Content-Disposition下载文件名）中携带非ASCII字符，协议规定必须使用特定的编码格式。有两种解决方案：
* RFC5987
* RFC2047

### RFC 8187-现代方案
这是目前官方推荐的标准方案，主要用于Content-Disposition响应头（控制文件下载）。
* 原理：在参数名后面加一个星号（*），表示该参数的值采用了特殊的编码格式。
* 格式：`参数名*=字符集'语言'经过URL编码的值`。`语言`部分一般省略。
* 示例：假如要文件名是`你好.txt`，则Header中有一行：`Content-Disposition: attachment; filename*=UTF-8''%E4%BD%A0%E5%A5%BD.txt`。

### RFC2047-MIME编码
* 格式：`=?字符集?编码方式(B/Q)?经过编码的数据?=`。`B`代表Base64编码，`Q`代表Quoted-printable编码。
* 示例：假如要文件名是`你好.txt`，则Header中有一行：`Content-Disposition: attachment; filename="=?UTF-8?B?5L2g5aW9?=.txt"`。

为什么RFC2047需要双引号（filename=后面跟着双引号）？
* 在HTTP协议（RFC 7230）中，Header的参数值分为两种：
  1. Token：简单的字符序列（如attachment），不需要引号。
  2. Quoted-string：包含特殊字符（如空格、分号、等号）的字符串，必须用双引号包裹。
* 示例中的`=?UTF-8?B?...?=`里面包含了`?`和`=`，这些在HTTP Header解析逻辑中属于“分隔符”，使用双引号可以防止解析器在错误的位置截断数据。

## Body
对于请求体中的数据，HTTP客户端可以通过在请求头中使用特定的字段来指定它的类型、格式等元信息：
* Accept-Encoding：客户端支持的压缩格式（客户端和服务端之间，对报文主体数据进行内容协商）
* Accept：客户端支持的数据类型和编码格式（客户端和服务端之间，对报文主体数据进行内容协商）
* Content-Type：请求体的数据类型和编码格式

对于响应体中的数据，HTTP服务端可以通过在响应头中使用特定的字段来指定它的类型、格式等元信息：
* Content-Type：响应体的数据类型和编码格式
* Content-Encoding：内容压缩
* Transfer-Encoding：分块传输

在HTTP/1.1规范中，如果没有明确指明报文主体的格式，则默认为ISO-8859-1（拉丁码表）。当前的Web开发中，如果不显式指定，默认共识已向UTF-8靠拢，但严格来说，依赖默认值是不符合规范风险规避原则的。
